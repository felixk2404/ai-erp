# משימות כתור פעולות אנושיות — עיצוב

תאריך: 2026-09-02. סטטוס: ממתין לאישור.

## מטרה

טבלת `Tasks` הופכת מרשימת to-do ידנית לתור של פעולות שהאוטומציה לא יכולה לבצע בעצמה. כל workflow שמגיע לנקודה שדורשת בן אדם (משלוח, הזמנת מלאי, שיחת טלפון, תיקון חשבונית) יוצר משימה. בעל העסק רואה את התור באפליקציה ומסמן "בוצע". סוכן המנהל יודע לענות "מה יש לעשות היום".

## סכימת Airtable

טבלת `Tasks` מקבלת שלושה שדות חדשים. השדות הקיימים (`Title`, `Status`) לא משתנים.

| שדה | סוג | ערכים |
|---|---|---|
| Source | Single line text | `order` / `stock` / `lead` / `invoice` / `manual` |
| RefId | Single line text | מזהה היעד: `ORD-0003`, מק"ט, `INV-0007`, record id של ליד |
| Created | Created time | מתווסף ידנית ב-UI (Metadata API לא תומך) |

עדכונים נלווים: `airtable/add-fields.sh` מוסיף את `Source` ו-`RefId`; `airtable/schema.md` ו-`airtable/verify-schema.sh` מתעדכנים. משימות שנוצרות מהאפליקציה מקבלות `Source=manual`.

## מי יוצר משימות

| workflow | מתי | Title | Source | RefId |
|---|---|---|---|---|
| WF10 הזמנה | אחרי `Create Order`, רק אם יש פריט פיזי | `לשלוח ORD-0003 ל{עיר}` | order | ORD-0003 |
| WF10 הזמנה | אחרי `Decrement Stock`, לכל מק"ט שהמלאי החדש שלו קטן מ-3 | `להזמין מלאי: {שם}, נשארו {N}` | stock | מק"ט |
| WF4 תשובות | אחרי `Mark Qualified` | `להתקשר ל{Name} ({Company})` | lead | record id של הליד |
| WF1 חשבוניות | בענף `Mark Error` | `לתקן INV-0007: {סיבת השגיאה}` | invoice | INV-0007 |
| WF5 טלגרם (ספק נפרד) | ליד חדש מתפריט הקטלוג | `לחזור ל{שם} — {מוצר}` | lead | record id של הליד |

כללים:

- **אין כפילויות למלאי.** לפני יצירת משימת `stock` מחפשים `AND({Source}='stock', {RefId}='{מק"ט}', {Status}='open')`. אם קיימת, לא יוצרים.
- **סף המלאי** הוא קבוע `3` בצומת Code של WF10. לא קונפיגורציה.
- **המשימה נוצרת אחרי ההודעה ללקוח,** לא לפניה. כשל ביצירת משימה לא מפיל הזמנה: הצומת מסומן `continueOnFail`, והשגיאה מגיעה ל-WF-Error כרגיל.
- כל יצירה היא צומת Airtable `create` רגיל, לא HTTP Request, כדי שהקרדנציאלס יישארו במערכת של n8n.

## שינויים ב-WF9 (סוכן המנהל)

`Build Context` מוסיף ל-JSON את `open_tasks`: עד 8 המשימות הפתוחות האחרונות, כל אחת `{title, source, ref}`. הפרומפט מקבל שורה: "משימות הן פעולות שהאוטומציה לא יכולה לבצע: משלוחים, הזמנת מלאי, שיחות ללידים, תיקון חשבוניות. כששואלים מה לעשות היום, ענה מתוך open_tasks". התרגום לעברית של `Source` נעשה בפרומפט (order=משלוח, stock=מלאי, lead=ליד, invoice=חשבונית, manual=ידני).

## שינויים באפליקציה

- `TaskFields` ב-`app/src/lib/types.ts` מקבל `Source?` ו-`RefId?`.
- מסך המשימות מציג לכל שורה תג מקור (אותו רכיב `StatusLed`/תג שכבר משמש ללידים) וקישור ליעד: `order` → `/customers` (עד שיש מסך הזמנות), `stock` → `/products`, `lead` → `/leads`, `invoice` → `/invoices`. הקישור נושא `?q={RefId}` כדי שהמסך יפתח מסונן, אם המסך תומך בחיפוש; אחרת קישור פשוט.
- הדשבורד: המונה הקיים של משימות פתוחות נשאר. רשימת "דורש טיפול" לא משתנה.
- יצירה ידנית נשארת ומקבלת `Source=manual`.

## טיפול בשגיאות

- כשל Airtable ביצירת משימה: לא חוסם את ה-workflow המקורי; מדווח ל-WF-Error.
- משימה שנוצרה לחשבונית שתוקנה ואומתה שוב: לא נסגרת אוטומטית. בעל העסק סוגר ידנית. (YAGNI; אפשר להוסיף אחר כך.)

## בדיקות

- **Vitest** באפליקציה: `statusMeta('Tasks', source)` מחזיר תווית עברית לכל מקור; טופס יצירה מוסיף `Source=manual`.
- **n8n**: `validate_workflow` על WF1, WF4, WF9, WF10 אחרי העדכון; `get_workflow_details` לאימות החיבורים.
- **קצה לקצה**: הזמנת בדיקה בחנות עם פריט פיזי שמלאיו יורד מתחת ל-3 יוצרת שתי משימות (משלוח + מלאי). הזמנה שנייה לאותו מק"ט לא יוצרת משימת מלאי נוספת. שאלה למנהל "מה יש לעשות היום" מחזירה את המשימות.

## מחוץ לתחום

- סגירה אוטומטית של משימות.
- תאריכי יעד ותזכורות.
